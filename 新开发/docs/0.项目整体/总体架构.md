# 总体架构（Pi Agent 与 Skill 产品方向）

> 状态：现行架构方向，实施范围见项目状态
> 适用日期：2026-11-07
> 不要据此实施：后端语言与运行入口以根目录 `PROJECT_STATE.md` 和本工作区现行需求为准；Pi Agent/Skill 产品方向作为背景参考。


## 一、项目总体定位

新的开发方向是构建一个**基于 Pi Agent 二次开发、以 Skill 为业务能力扩展核心、采用 Python 后端与 TypeScript 前端的智能业务应用系统**。

整体采用 **前端交互层 + Agent 智能编排层 + 后端业务服务层 + 数据存储层** 的分层架构，将 Agent 的智能决策能力与后端确定性业务执行能力解耦。

核心设计思想：

1. **Agent 层基于 Pi 二次开发**：复用 Pi 的 Agent Loop、Tool Calling、Session、Context Management、Skill 加载及 Extension 机制，避免从零开发 Agent Harness。
2. **Skill 作为核心业务扩展机制**：将业务能力封装成可发现、可加载、可执行的 Skill，使通用 Agent 能够根据用户意图动态调用专业能力。
3. **Skill + Script + Backend API**：在 Skill 内封装 TypeScript 脚本，通过 JSON 参数调用后端 API/MCP，无须为每个业务接口单独注册 Tool。
4. **Agent 与业务后端解耦**：Agent 负责理解需求、规划任务、选择 Skill、构建请求以及整合结果；后端负责数据库查询、业务计算、规则校验、RAG 检索等确定性操作。
5. **技术边界**：React 前端和 Pi 相关脚本使用 TypeScript，业务 API 与 Worker 使用 Python。

## 三、重点：基于 Pi 的 Agent 二次开发

Agent 层不从零实现，而是直接基于 Pi SDK 和 Extension API 进行扩展。

重点开发内容：

- **Agent Loop**：复用 Pi 原有的模型推理与工具调用循环。
- **Skill 管理**：实现业务 Skill 的注册、发现、加载与执行。
- **Context Engineering**：管理系统指令、历史会话、Skill 内容、工具响应及业务上下文。
- **Session Management**：管理用户会话、状态持久化和历史恢复。
- **Tool Execution**：通过受控的脚本执行工具运行 Skill 内的 TypeScript 脚本。
- **Task Planning**：根据用户问题选择单个或多个 Skill，完成业务编排。
- **Streaming**：通过 SSE/WebSocket 将 Agent 的响应与执行状态传递给 React 前端。
- **Extensions**：利用 Pi 扩展机制实现工具权限控制、调用监控及自定义行为。

重点是复用 Pi 的通用 Agent 能力，将开发精力集中在业务 Skill 体系及 Agent 与后端的协作机制。

## 四、核心：Skill 设计方案

### 4.1 Skill 的定位

Skill 不仅是传统意义上的任务指导文件，还承担业务能力封装、接口调用指导和工作流组织的职责。

一个 Skill 可以包含：

- **SKILL.md**：定义 Skill 的用途、触发条件、参数规范、执行步骤和业务约束。
- **scripts/**：封装 API/MCP 请求，实现 JSON 参数接收、数据校验、后端调用和结果输出。
- **references/**：存储复杂业务规则、接口说明、数据结构及补充资料。

示例目录：

```text
skills/
├── product-query/
│   ├── SKILL.md
│   ├── scripts/
│   │   └── query.ts
│   └── references/
│       └── schema.md
│
├── cash-value/
│   ├── SKILL.md
│   └── scripts/
│       └── calculate.ts
│
└── product-comparison/
    ├── SKILL.md
    └── references/
        └── workflow.md
```

### 4.2 Skill 分类

**执行型 Skill**

负责完成明确的业务操作，通常包含调用后端 API 的脚本，例如：

- 产品信息查询 Skill
- 现金价值查询 Skill
- 保费计算 Skill
- 保险条款检索 Skill
- PDF 文档处理 Skill

**编排型 Skill**

负责指导 Agent 将多个业务能力组合为完整工作流，例如：

- 保险产品对比 Skill
- 产品利益演示 Skill
- 综合条款分析 Skill

编排型 Skill 主要负责业务流程和任务组织，执行型 Skill 主要负责具体业务能力调用。两类 Skill 不要求严格一一对应后端接口。

### 4.3 Skill 的执行机制

```text
用户自然语言请求
        ↓
Pi Agent 理解用户意图
        ↓
根据名称和 description 匹配 Skill
        ↓
读取 SKILL.md
        ↓
提取用户参数，构建 JSON
        ↓
调用基础 Tool 执行 Skill Script
        ↓
Script 解析 JSON 并校验参数
        ↓
通过 HTTP / MCP 调用后端
        ↓
后端执行确定性业务逻辑
        ↓
Script 输出结构化 JSON
        ↓
Agent 解析执行结果并生成回复
```

Agent 不需要为每个业务 API 注册独立 Tool。

最小工具能力为：

1. **Skill 文件读取能力**：可由 Pi 自带的 Skill 加载机制提供。
2. **脚本执行能力**：通过 Shell、受控 TypeScript 执行器或其他基础 Tool 运行脚本。

Agent 可以通过 stdin 向脚本传递 JSON，并通过 stdout 接收 JSON 结果。

推荐统一调用契约：

```json
{
  "product_id": "A001",
  "age": 30,
  "policy_year": 10
}
```

统一返回契约：

```json
{
  "success": true,
  "data": {},
  "error": null
}
```

脚本只负责请求封装与必要的数据转换，核心业务计算、权限检查和最终参数校验仍由后端负责。

### 4.4 Skill 工程化设计原则

- **按需加载**：通过 Skill 元数据完成初步发现，需要时再加载完整说明和参考文件。
- **职责清晰**：Skill 负责业务语义与流程，Script 负责调用，Backend 负责实际业务执行。
- **接口标准化**：使用 JSON Schema / Pydantic 等定义和校验参数，减少 LLM 构建错误请求的风险。
- **脚本复用**：多个 Skill 可以复用统一的 API Client。
- **最小权限**：限制可执行脚本和可访问的后端接口，避免赋予 Agent 不必要的终端权限。
- **异常处理**：统一错误码、超时、重试策略与结构化响应。
- **可评估性**：分别评估 Skill 选择准确率、参数提取准确率、脚本执行成功率、后端结果正确率与最终任务完成率。
- **可移植性**：尽量减少对单一 Agent Harness 私有能力的依赖，使 Skill 能够迁移到其他兼容平台。

### 5.1 存储层规划

**MySQL：关系型业务主库（已确定）**

主要负责：

- 保险公司与产品信息管理
- 产品条款及文档元数据
- 费率表、现金价值表等结构化业务数据
- 产品规则与计算参数
- 用户业务记录
- 需要持久化的业务状态及关联关系

**向量数据库：待选型**

主要负责：

- 保险条款及说明书的向量索引
- 语义相似度检索
- 结合产品 ID、文档类型等元数据进行过滤
- 支持 RAG 检索、召回及重排链路

候选方向包括 Milvus、OpenSearch、Qdrant 等，暂不确定最终方案。后续需要根据数据规模、混合检索能力、过滤能力、部署成本及 TypeScript SDK 支持情况进行评估。

**Redis：缓存与辅助状态**

负责高频查询缓存、任务状态、限流计数及必要的临时数据。

**MinIO：对象存储**

负责原始 PDF、文档解析产物、图片、附件等文件的存储。

首轮 MySQL、Redis、MinIO 统一以 Docker Compose 部署（`新开发/infrastructure/docker/`），不使用本机 MySQL 实例；启动与连接说明见该目录 README。

## 七、开发优先级

首轮已确认采用统一 Crawler Core 与 Company Adapter：协会独立适配器负责主索引，Company Adapter 根据已有公司和产品寻找官网资料，Core 统一管理调度、请求、下载、重试及持久化。MySQL 产品库与采集运行库分开，Redis 提供队列，MinIO 保存 PDF 和来源快照。先验收 P1，再逐家公司接入 P2；接口与验收设计见 [P1/P2 开发细则](../1.信息接入与资料获取/P1-P2开发细则.md)。

用户确认按模块开发，首轮优先完成任务书中的 P1、P2：产品主数据库、官网资料获取模块及可交互测试 Web 中台。首轮内部使用，设计考虑后续上线的并发与异步能力；具体范围、接口、任务机制和验收标准待进一步确定。官网资料获取及来源记录已纳入首轮目标。

Pi Agent、Skill、RAG、文档结构化和确定性计算仍是总体方向，按后续业务优先级逐步建设，不以前置完成 Agent 基础设施作为 P1/P2 的条件。

## 八、最终开发目标

项目的核心不只是开发一个具有聊天功能的 AI 应用，而是建立一个**基于 Pi Agent 的、以 Skill 为主要能力扩展单元的业务 Agent 平台**。

最终形成以下架构模式：

**React 前端负责交互 → Pi Agent 负责理解与编排 → Skill 负责业务能力描述和调用封装 → Python 后端负责确定性执行 → MySQL 及其他数据存储组件负责持久化与检索。**

其中，**Pi 二次开发和 Skill 体系设计是整个项目最重要的技术研究与开发重点**；Python 后端和 TypeScript 前端则负责提供统一、可维护、可扩展的工程基础。
