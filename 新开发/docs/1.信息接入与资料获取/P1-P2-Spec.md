## 问题陈述

项目要在内网首轮交付一个可持续运行的系统：从中国保险行业协会人身保险产品信息库建立全国人身保险产品主索引，再按公司名和产品名到各保险公司官网找到条款、费率表、现金价值表、说明书等原件，保存可核查的来源与快照，并让项目成员在 Web 中台发起采集、查看进度、浏览产品、检查资料缺口、处理人工确认。

目前只有文档、没有代码。手工方式无法持续覆盖：协会库只能按类别（必选）加公司名、产品名（模糊、可空）查询，且不提供本项目所需的原件下载；各公司官网入口和页面结构不同，附件散落在目录页、详情页和公告中；资料归属、版本更替、共用文件、销售状态都容易判断错。缺少来源记录时，无法证明某份 PDF 属于哪款产品，也无法在采集结果变化后解释差异。因此需要一套统一的采集核心加逐家公司适配器，以及一个可查询、可操作、可确认的中台。

## 解决方案

工作区包含 React 中台、Python 业务 API 与使用 BullMQ 的 Python 采集 Worker。采集分成两条清晰链路：

- **P1 主索引**：协会 Adapter 按类别分页读取公司名、产品名、销售状态和来源，写入 MySQL 产品库；中台提供公司、产品查询和采集任务操作。
- **P2 资料获取**：Company Adapter 根据主索引已有产品，在对应公司官网目录与详情页发现附件候选；Crawler Core 统一下载、识别格式、保存快照、按内容去重、写入文件与来源；有明确官网依据时建立产品资料关联，归属不明时进入待确认。

产品库与采集运行库分开（同一 MySQL 实例下两个库），Redis 提供任务队列与跨 Worker 的按官网限流，MinIO 保存 PDF 与来源页面快照。MySQL、Redis、MinIO 统一以 Docker Compose 部署，不使用本机 MySQL 实例。人工更正受保护：后续采集发现差异时生成提示，不直接覆盖已确认值。P1 验收通过后再逐家公司扩展 P2，新增公司以新增 Adapter 和配置为主。

## 实现决策

### 1. 工程形态与模块

- Web 使用 pnpm workspace，后端使用独立 Python 虚拟环境。
- 模块划分：
  - **Web 中台**：React + TypeScript，产品、公司、任务、待确认、运行设置页面，PDF 预览。
  - **业务 API**：Python + FastAPI，Pydantic 参数校验，内部令牌认证，SSE 进度推送。
  - **采集 Worker**：BullMQ Worker + Crawler Core，承载任务执行、断点、取消与限流。
  - **接口契约**：公开 HTTP 输入、输出、状态与错误码，供 Web 与后端对接。
  - **数据访问**：MySQL SQL 与仓储，产品库和运行库分别连接，不混用表。
  - **适配器**：协会 Adapter 与公司 Adapter 注册表均位于 Python 后端。
- 启动入口为 `pnpm dev:web`、`pnpm dev:api` 和 `pnpm dev:worker`。
- 配置来自环境变量与环境示例文件；MySQL、Redis、MinIO 使用新项目独立配置，不迁移旧数据。

### 2. 数据模型（产品库）

主键统一为数字自增；时间使用 UTC 保存；名称匹配字段与展示字段分开。以下为表职责与必须表达的字段，最终 DDL 在实施时细化，但不改变职责划分。

| 表 | 关键字段与约束 |
| --- | --- |
| company | 公司名称（清理空白后唯一）、官网地址、资料入口地址、备注；官网未知时允许为空并标记待补 |
| product | 所属公司、产品名称、规范化名称、产品分组（individual / stopped）、同名协会记录数、分组销售状态、状态获取时间、销售状态上一次原始值（用于识别来源值变化）、人工确认的销售状态与确认时间（可空）、人工更正说明（可空）、官网产品代码与备案号（可空，确实取得时保存）、最近索引来源地址和类别上下文；不设"公司+名称"唯一约束 |
| product_index_record | 所属产品、协会记录标识及稳定去重键、来源名称、规范化名称、协会原始销售状态与规范状态、销售时间原文、获取时间、来源地址、类别上下文、官网产品代码与备案号；同一协会记录在公司内唯一 |
| document | 所属产品（归属未决可空）、资料类型、当前或历史、文件名、格式、存储位置、字节数、内容哈希、产品网页地址、下载地址、标题、创建和更新时间 |

- 资料按所属产品分别登记；相同内容可有多条产品资料记录，MinIO 按内容哈希复用文件对象。
- 每次来源快照索引按任务保存在采集运行库，文件共用时通过产品编号记录关联；旧来源无法可靠确认任务时保留为空。
- 文件内容哈希只用于去重，不作为业务主键，也不用于跨产品合并判断。
- 采集值与人工确认值分列保存：展示时人工确认值优先；后续采集发现差异只生成待确认项，不覆盖确认值。
- 差异提示区分两类，判据所需的值一并写入待确认项候选数据：本次采集值与人工确认值不同（人工更正被来源挑战）；本次原始值与上一次原始值不同（来源口径本身发生变化）。
- 产品库不保存任务、重试、网络错误、调试日志等采集中间态。
- `product.same_name_count` 表示同一公司和规范化名称下不同协会记录的数量，包括在售记录；同一名称有多个在售记录时仍保留各自产品 ID。
- 同一公司、同一规范化名称且协会状态明确为停售或停用的记录合并到一个 `stopped` 产品；协会记录各自在 `product_index_record` 保留原始状态、销售时间和来源。停用与停售只在产品归组时同组，不改写来源含义。
- 在售和未知状态记录各自保留独立产品 ID，不并入停售产品组。官网资料若明确属于同名停售产品，关联到该停售产品 ID；不推断文件与组内单条协会记录的对应关系。

### 3. 数据模型（采集运行库）

- **crawl_task**：任务类型（协会主索引 / 公司资料获取）、范围、启动时配置快照、状态、计数、父子任务关系、时间戳。
- **crawl_task_unit**：处理单元及断点。索引任务以（类别，页序号）为单元并保存下一游标；资料任务以（公司，产品）为单元并保存已搜索页面列表。单元保存状态、尝试次数、最后错误、更新时间。
- **review_item**：待确认类型（产品身份、资料归属、来源值变化、人工更正差异）、关联任务、候选数据（含本次采集值、上一次来源值与当前人工确认值）、来源、状态、处理结果、处理时间。
- **app_setting**：运行设置（并发、访问间隔、超时、重试、定时计划、协会采集开关）。
- 待确认候选项保存在运行库；人工确认后才写产品资料关联。运行日志写入日志存储，不进产品库。

### 4. 适配器契约

契约沿用细则草案，二者保持一致：

```ts
interface AssociationAdapter {
  listCategories(ctx: CrawlContext): Promise<Category[]>;
  readPage(
    input: { category: string; cursor?: string },
    ctx: CrawlContext
  ): Promise<{ products: IndexProduct[]; nextCursor?: string; reportedTotal?: number }>;
}

interface CompanyAdapter {
  key: string;
  discoverDocuments(
    input: { company: Company; products: ProductRef[]; cursor?: string },
    ctx: CrawlContext
  ): Promise<{ candidates: DocumentCandidate[]; nextCursor?: string; searchedPages: string[] }>;
}
```

- `IndexProduct` 携带公司名、产品名、销售状态原始值与规范值、来源地址、获取时间；源站有稳定记录标识时另存，不替代数字主键。
- `DocumentCandidate` 携带候选产品 ID、资料类型或待定类型、标题、下载地址、来源页面、支持关联的页面文字或附件关系、页面快照内容。多个候选 ID 不自动意味着共用。
- `CrawlContext` 只提供取消信号与日志，不暴露数据库连接；网页读取、按域名限流与浏览器渲染由 Core 以站点入口端口（`AssociationSourceGateway` / Company 侧同名端口）注入，Adapter 只依赖端口、不直连网络。这比细则草案里"Context 自带 HTTP 客户端"更窄，便于用内存端口跑契约测试。
- 协会详情页需要验证码且不提供本项目所需原件，首轮不接入详情与原件下载；不使用绕过验证码的方式。
- 适配器不硬编码产品名、文档 ID 或一次性哈希脚本地址；脚本地址变化按页面结构变化处理并记录失败。

### 5. 匹配、归属与版本

- **公司**：用可维护的名称映射匹配索引公司。主索引出现未登记公司时自动建立公司记录（名称为准，官网留空待补），不猜测官网地址；补录官网后才可执行该公司资料任务。
- **产品**：在同公司范围内按规范化名称匹配。规范化只处理首尾空白、连续空白、全半角数字与括号等展示差异，不删除年份、版本、附加险等有业务含义的词。
  - 有协会记录标识时按标识幂等更新 `product_index_record`；协会原始状态与销售时间逐记录保存。
  - 明确在售记录各自对应独立产品；同名不构成合并依据。
  - 明确停售或停用记录按同公司和规范化名称归入同一个 `stopped` 产品；分组状态显示为“停售/停用”，各来源记录的原始状态仍可分别核查。
  - 未知状态记录各自保持独立产品，不据此加入停售组。
  - 没有稳定来源标识时使用可重复计算的来源内容键去重；若来源内容不能区分多条记录，则不据名称之外的证据猜测其条数。
  - 同公司任务串行执行，避免并发重复创建；重复执行由上述规则保证幂等。
- **资料归属**：仅当来源页面文字或附件关系明确支持某产品时才自动建立关联。候选产品不唯一、只有名称相似或页面关系不清时，保存文件与来源并生成归属待确认项，确认前不指定 document 的产品归属。
- **共用资料**：官网明确说明一份资料适用于多产品时，文件只保存一份，按产品分别建立关联并分别保留来源。
- **版本**：可判定为同一来源（同一来源标识或同一地址，或官网明确版本关系）且内容哈希变化时，新建 document 资料记录，旧资料标记为历史；版本关系不明时并存为当前资料，不自动替换。
- **销售状态**：保存原始值与规范值；来源未明确说明时为未知。单次未找到不构成停售或删除依据。跨类别重复命中只更新同一产品与最近索引来源。
- **人工更正**：通过 `PATCH /api/products/:id` 写入人工确认的销售状态、产品名称与更正说明，并记录确认时间与操作者；确认值与采集值分列保存，后续采集只生成差异待确认项，不覆盖确认值；处理待确认项时可以选择采用采集值、保留确认值或重新确认。

### 6. 下载、格式检查与来源留存

- PDF 下载走独立下载路径，显式接受响应类型，处理重定向、超时与大小上限；不假设通用页面爬取组件默认处理 PDF。
- 格式检查限于：响应成功、内容非空、魔数为 PDF（或等价的可信类型判断）、未返回登录页或错误网页。首轮不解析正文、不抽取表格。
- 通过检查后按内容哈希去重：已存在则复用 document；不存在则写 MinIO 并创建记录。
- 来源快照内容保存在对象存储中；运行库 document_snapshot 按任务记录快照位置、来源响应地址、下载地址、获取时间和内容类型。产品网页地址仅在能明确取得时写入 document.source_url。
- 下载失败按网络、HTTP 状态、超时、格式、空文件分类记录，供中台展示和重试；失败不创建 document。

### 7. 调度、并发与断点

- Redis + BullMQ 承载任务队列与定时触发；任务类型分为协会主索引与公司资料获取，按类型配置 Worker。
- 全局并发和按公司域名访问频率共同生效；按域名限流在 Redis 中共享，多个 Worker 不能放大同一官网的总限额。
- 同公司同类型任务未结束时进入排队，Worker 按公司串行；不同公司可以并行。
- 处理单元的结果和完成状态先落库，再确认队列任务完成；恢复时跳过已完成单元，允许重复读取但写入幂等。
- 页面临时失败由请求层有限重试；耗尽后记录该项失败并继续其他项。任务层重试只处理进程或基础设施异常，恢复未完成项，不因单页失败重跑整批。
- 取消停止新工作并尽可能中止活动请求；已保存结果保留，任务状态为已取消。续跑与重试跳过已完成项。
- 定时触发集中在调度层，Adapter 不自行定时；首次启动不自动触发全库采集。
- 首轮初值建议：全局并发 2、单域名每秒 1 次请求、单请求超时 30 秒、请求层最多 3 次；作为起点配置，小规模实测后调整，不作为性能承诺。

### 8. 状态口径

| 对象 | 状态 |
| --- | --- |
| 任务 | 排队、运行、完成、部分失败、失败、已取消 |
| 产品某类资料 | 尚未执行、未找到、已下载、下载失败、归属待确认；中断附原因 |
| 销售状态 | 在售、停售/停用组、未知（协会记录逐条保留原始值与获取时间） |
| 产品资料 | 当前、历史；版本关系不明时不自动替换当前资料 |

- "未找到"仅指本轮已搜索范围内未找到。"不适用"必须有明确来源或人工确认，不能从缺失倒推。
- 资料情况由已关联资料与最近运行结果合并展示；产品表不保存重试和网络错误。
- 任务运行完成不等于四类资料齐全；覆盖、任务完成率、资料获取情况分别统计并注明分母。

### 9. 中台与 API

API 按资源分组，统一放在 `/api` 前缀下，均为 JSON；错误返回稳定的错误码与消息；列表统一分页与排序；除健康检查外都要求内部令牌，未登记路径同样默认拒绝。

| 方法与路径 | 用途 |
| --- | --- |
| GET /api/categories | 协会类别列表（任务范围选择与来源上下文） |
| POST /api/crawl-tasks | 创建任务（类型、公司/产品/类别范围、可选配置覆盖），立即返回数字任务 ID |
| GET /api/crawl-tasks | 任务列表，按状态、类型、公司筛选 |
| GET /api/crawl-tasks/:id | 任务详情、进度、单元与失败摘要 |
| GET /api/crawl-tasks/:id/events | SSE 推送任务进度与完成事件 |
| POST /api/crawl-tasks/:id/cancel | 取消任务 |
| POST /api/crawl-tasks/:id/retry-failed | 以失败单元为范围创建重试任务，记录父子关系 |
| POST /api/crawl-tasks/:id/resume | 续跑中断任务 |
| GET /api/companies、POST /api/companies、PATCH /api/companies/:id | 公司列表与官网、资料入口维护 |
| GET /api/products | 按公司、名称、销售状态、资料情况筛选；返回同名协会记录数 |
| GET /api/products/:id | 产品详情：基础信息、协会记录明细、四类资料、当前与历史关联、来源与快照 |
| PATCH /api/products/:id | 人工更正：确认的销售状态、产品名称与更正说明 |
| GET /api/documents/:id/file | 原件下载或内联预览 |
| GET /api/documents/:id/sources | 文件的来源列表与快照 |
| GET /api/review-items、POST /api/review-items/:id/resolve | 待确认项列表与处理（合并、新建、指定归属、忽略、采用采集值） |
| GET /api/settings/runtime、PUT /api/settings/runtime | 并发、频率、超时、重试、定时计划、协会采集开关 |
| GET /api/reports/coverage | 覆盖与失败报告（按任务或按公司） |
| GET /health | 健康检查，不需要令牌 |

- 任务创建后立即返回，进度通过 SSE 推送；断线后重新查询任务状态即可恢复。
- 人工确认记录处理时间与操作者标识（首轮为内网令牌标识，不建多用户账号体系）。
- 设置修改对新任务生效；运行中任务按启动时的配置快照执行，避免中途行为漂移。
- Web 页面包含产品列表与详情、公司管理、采集任务、待确认事项、运行设置；产品页显示同名协会记录数及组内来源记录，并支持原件预览、来源与历史资料。

**M3 逐家扩展与运行验证**：以同一套契约接入至少两家公司，验证多任务并发、单域名限流、失败重试、取消、进程重启续跑与重复任务结果不重复；新增公司不改 Core、不按产品写专属规则。覆盖与失败统计分别按公司、产品、资料类型给出，明确分母。

## 测试决策

**好测试的标准**：只断言外部可观察行为——适配器对给定页面返回什么、API 对给定请求返回什么、数据库和对象存储里最终留下什么；不依赖内部函数调用顺序、SQL 文本、选择器细节或队列内部结构。

**Seam 1：Adapter 契约（主 seam）**

- 对协会 Adapter 和每个公司 Adapter 运行同一套契约测试：输入录制的页面样本（HTML/JSON/文件）与假的 `CrawlContext`，断言返回的产品、候选、来源上下文、游标和错误分类。
- 样本按适配器版本存放在测试固定目录（`fixtures/<adapter>/`），作为回归基线；页面结构变化时先更新样本再改实现。ticket 07 负责把首批录制样本落到该目录。
- 覆盖：首页、中间页、末页（无下一游标）、源站报告总数、错误网页、空结果、重复记录、跨页重复、取消信号触发、无 JavaScript 与需要浏览器两类路径（后者用同一份渲染后样本）。已建立部分见"既有先例"，其余跟随 ticket 04/07 补齐。
- 假 `CrawlContext` 只提供取消信号与测试日志；页面数据由假 `AssociationSourceGateway` 端口提供（内存映射，可触发取消、可注入错误），契约测试不连接数据库、Redis、MinIO 或真实站点。

**Seam 2：HTTP API（业务级）**

- API 测试使用 FastAPI 测试客户端或实际 HTTP 服务。切片 01 用内存实现验证认证与健康检查；从 ticket 02 起 API 测试连接真实 MySQL 测试库（独立测试库或每用例事务回滚，由 02 定案），Redis 与 MinIO 在 ticket 08/12 引入。
- 覆盖：创建任务与立即返回 ID；任务状态流转；重复执行不重复产品/文件/关联；销售状态原始值保留；人工更正后差异生成待确认项且不覆盖；归属歧义只保存文件与来源、不建关联；共用文件一份多关联；版本变化保留历史；取消、重试失败单元、重启续跑；格式错误记为下载失败；SSE 事件顺序；无令牌 401（含未登记路径）；报告分母正确。
- API 测试断言用户可见结果（响应、列表、详情、文件与快照是否存在），不断言任务内部重试次数或队列实现。

**不测试**：React 组件的像素与样式、BullMQ/Crawlee 的库内部行为、SQL 查询文本、真实协会与公司官网（联网检查另记）。

**运行方式**：Web 使用 `pnpm test` 和 `pnpm typecheck`；Python 测试使用 `unittest discover`，集成测试连接隔离的 MySQL、Redis 和 MinIO。见[运行说明](../../README.md)。

**既有先例**：协会主索引 Adapter 的 6 项契约测试（分类、产品映射与状态原始值、游标分页、来源不可用、取消、分类失败）与 API 的 3 项测试（健康检查、默认拒绝、令牌校验）已建立；契约测试使用假 SourceGateway，页面样本为构造数据，真实样本随 ticket 07 落地。API 测试仍为内存实现，真实存储 seam 从 ticket 02 开始。不引用旧实现的测试作为基线。

**联网验证**：按类别与页面范围、按公司，在真实站点执行小规模检查并记录日期、范围、结果与失败；与构造测试分开报告。
