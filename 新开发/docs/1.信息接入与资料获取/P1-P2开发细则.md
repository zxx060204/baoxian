# P1/P2 开发细则

> 状态：现行（业务与存储边界已确认；接口与实施设计已由 [P1/P2 实现规格](P1-P2-Spec.md) 承接）
> 适用日期：2026-11-17
> 不要据此实施：接口契约与实施设计以规格为准，本文只保留已确认边界与来源。

## 已确认目标与范围

按模块优先建设产品主数据库（P1）、官网资料获取（P2）及可交互测试 Web 中台。全国人身保险公司与产品持续覆盖是目标；逐家公司接入，以实际发现、下载和失败统计说明覆盖情况。首轮内部使用，设计支持未来上线及并发、异步任务。

首轮收束为人身保险。由中国保险行业协会人身保险产品信息库发现产品，获取公司名、产品名与在售情况，覆盖该来源可查询的在售、停售及历史产品。没有明确状态时保留未知；单次未找到产品不构成停售或删除依据。

获取产品详情、条款、费率表、现金价值表、产品说明书及相关附件。资料保留来源页面、原始下载地址、获取时间等信息，支持从产品追溯原件与来源。

## 产品主库约束

发现流程已确定为：**协会人身保险产品信息库 → 产品主索引 → 根据公司名与产品名到对应保险公司官网获取 PDF → 关联产品并保存来源**。协会负责主索引来源，公司官网负责资料获取，不采用官网独立发现产品并加入主索引的首轮路线。

用户已实测确认可仅选择产品类别查询；协会主索引的业务输入按公司名、产品名与在售情况设计，不把备案号、产品代码或原件下载作为该入口的必备能力。内部数字 ID、来源地址与获取时间仍正常保存。该库不承担 PDF 原件下载，相关资料在公司官网查找。

[调研记录](中国保险行业协会产品信息库调研.md)区分公开前端静态证据与用户实测。完整分页、分类覆盖与跨类别重复仍需在接入时验证，不将单次搜索结果数直接视为全国覆盖量。不同来源出现信息差异时保留来源，不静默覆盖已确认信息。

- 采用 MySQL 方向，表与字段保持简洁、可读，在保持业务能力的前提下减少不必要的结构。
- 主键采用数字自增；官网产品代码、备案号等独立保存，不以哈希作为主键。
- 产品主库只保存产品、资料及必要的来源与业务关联；采集任务、重试、调试等与产品无关的中间态独立管理，不混入产品库。
- 自动入库；产品身份、版本或资料归属有歧义时保留候选及来源，供中台人工确认，不自动合并。
- 必要的参数、引用及文件格式检查即可，不建设繁重的校验流程。

## 更新和文件边界

支持中台手动发起与定时增量采集。更新最新信息，重复采集不重复建立产品记录；同一地址文件发生变化时保留新旧文件及来源，产品默认展示最新资料并支持查看历史。

首轮文件检查限于能否正常下载、格式是否正确，包括识别下载响应是否实际为错误网页。费率表、现金价值表及正文深度解析交由后续模块，不作为 P1/P2 获取成功的前提。

### 共用 PDF 与来源留存

用户调研确认，共用 PDF 主要出现在附加险或组合销售场景。官网有明确适用依据时，一份 PDF 可以关联多款产品，文件只保存一份；不能仅根据名称相似建立关联。附加险产品仍是独立产品，共用资料不表示这些产品应合并。

保留直接支持资料归属的产品详情页或资料列表页快照，以及来源 URL、原始下载地址和获取时间。快照与 PDF 文件存放于文件存储，产品库仅保存必要的元数据和关联；抓取过程及调试日志独立管理。

## 中台范围

支持发起采集、查看任务进度和错误、浏览公司与产品、检查资料来源与缺口、处理人工确认事项。

允许人工更正产品信息、销售状态和资料归属。人工确认过的更正保留，后续采集内容不同时提示差异，不直接覆盖；只保留必要的更正信息与来源，不引入复杂审批。

支持按全部已接入公司、指定公司或指定产品发起采集，并支持取消、失败项重试和中断后续跑。并发数、公司访问频率、定时计划可配置。采集在后台异步执行，中台持续展示进度；单家公司或文件失败不阻塞其他任务。

## 实现约束

前端使用 TypeScript，后端 API 与采集 Worker 使用 Python。经用户确认的旧模块可按需接入。

## 已确认的存储职责

采用 MySQL、Redis 和 MinIO。三者以 Docker Compose 部署（`新开发/infrastructure/docker/`），不使用本机 MySQL 实例；同一 MySQL 实例下使用独立的产品库与采集运行库；Redis 管理待执行任务及临时调度状态，MinIO 保存 PDF 和来源页面快照。具体连接与账号在环境落地时配置，不调整旧数据库。

用户已确认以下核心表职责，字段与 DDL 在实现设计中细化：

| 表 | 保存内容 |
| --- | --- |
| company（公司） | 公司名称、官网及资料入口 |
| product（产品） | 所属公司、产品名称、协会在售情况及索引来源信息 |
| document（文件） | 所属产品、资料类型、当前/历史状态、文件名称、格式、存储位置、大小、内容哈希、产品网页地址、下载地址、标题与时间；数字主键 |

同一文件属于多个产品时分别保存资料记录，文件对象按内容哈希复用；各次来源响应和快照索引按任务保存在运行库。文件更新后保留新旧文件及来源，不因文件版本变化复制产品。产品人工更正及差异处理使用必要字段或记录表达，不预建通用审批系统。细化字段时仍需检查上述划分能否完整表达来源与产品关联，不以固定表数限制业务。

采集运行库独立保存任务、进度、断点、失败原因及来源快照索引；快照内容保存于对象存储。

## 已确认的模块顺序

先完成并验收 P1：协会分类分页采集、主索引入库、在售状态更新及中台查询。随后逐家公司完成 P2：官网资料发现、下载、产品关联、来源留存和任务操作。建设统一 Crawler Core 与 Company Adapter。

资料结果分别展示已下载、未找到、下载失败和归属待确认；任务运行完成不等于产品四类资料齐全。未接入官网、尚未执行、任务取消或中断不得显示为未找到。

## Crawler Core 与 Adapter 设计（待整体审阅）

### 模块边界

```text
React 中台 → Python API → BullMQ 调度 → Python Worker
                                      ├─ Association Adapter → 协会主索引
                                      └─ Company Adapter → 官网附件候选
                         ↓
              下载、格式检查、来源留存、资料关联
                         ↓
       产品库 / 采集运行库 / MinIO（Redis 提供任务队列）
```

| 模块 | 输入 | 输出 | 状态与副作用 |
| --- | --- | --- | --- |
| 任务 API | 任务类型、公司/产品范围、运行配置 | 数字任务 ID | 写运行库并入队，长时间采集在后台执行 |
| Crawler Core | 已保存任务、适配器及断点 | 执行进度、产品或文件结果 | 统一请求、并发、下载、重试、取消、断点与持久化 |
| Association Adapter | 产品类别、分页位置 | 公司名、产品名、在售情况、来源定位、下一页位置 | 通过 Core 客户端读网页或接口，不直接写库或下载资料 |
| Company Adapter | 官网配置、主索引产品、可选分页位置 | 附件候选及支持归属的来源上下文 | 通过 Core 客户端读取官网，不直接写库或创建新产品 |
| 文件与来源服务 | 候选地址、来源页内容、产品关联 | 文件 ID、来源记录和已确认关联 | 下载 PDF、检查格式、写 MinIO 与业务元数据 |
| 产品维护服务 | 人工更正或归属确认 | 更新后的产品/资料 | 保留人工更正；采集差异待处理，不覆盖确认值 |

Core 复用成熟的请求、浏览器及任务队列组件，业务层组织共同流程。Company Adapter 可使用该官网的选择器、公开接口和分页方式；不按具体产品名或文档 ID 编写专属提取规则。新公司接入以新增 Adapter 和配置为主，不复制调度、下载、存储代码。

### 接口契约草案

> 状态：历史记录（草案）。以下仅为设计示意；现行契约以 [P1/P2 实现规格](P1-P2-Spec.md) 的"适配器契约"为准（`CrawlContext` 只保留取消信号与日志，网页读取与限流由 Core 通过站点入口端口注入）。

以下仅为设计示意，尚无实现代码：

```ts
interface AssociationAdapter {
  listCategories(ctx: CrawlContext): Promise<Category[]>;
  readPage(input: { category: string; cursor?: string }, ctx: CrawlContext):
    Promise<{ products: IndexProduct[]; nextCursor?: string; reportedTotal?: number }>;
}

interface CompanyAdapter {
  key: string;
  discoverDocuments(input: {
    company: Company;
    products: ProductRef[];
    cursor?: string;
  }, ctx: CrawlContext): Promise<{
    candidates: DocumentCandidate[];
    nextCursor?: string;
    searchedPages: string[];
  }>;
}
```

- `IndexProduct`：公司名、产品名、协会原始及规范销售状态、销售时间原文、来源地址、获取时间和类别；协会记录标识可用时另存，不替代数字主键。
- `DocumentCandidate`：候选产品 ID、资料类型或待定类型、标题、下载地址、来源页面、支持关联的页面文字/附件关系及快照内容。多个候选 ID 不自动意味着共用，确认依据后再关联。
- `CrawlContext`：HTTP/浏览器客户端、访问频率控制、取消信号及日志。Adapter 不拥有数据库连接；文件统一交给 Core 下载。

按公司复用目录读取，避免为每款产品重复扫描整个官网。官网目录用于在主索引已有产品中寻找附件，不成为额外产品入库来源。

### 匹配、版本与存储细节

公司使用可维护的名称与官网映射。产品在同公司范围内按名称及明确页面关系匹配，只清理空白等展示差异，不删除年份、版本或附加险等有业务含义的词。

跨类别重复采集更新同一协会产品记录；有稳定来源标识时利用该标识。明确在售及未知状态的同名记录继续保留不同产品 ID；同一公司、同一规范化名称下的停售/停用记录合并到一个停售产品组。产品字段记录同名协会记录数，组内每条协会记录仍分别保存协会标识、状态原文、销售时间和类别等来源信息。没有稳定标识时按可重复来源内容去重，不从名称推断条数。官网产品代码、备案号确实取得时作为补充字段，不依赖 PDF 深度解析来填充。

新内容生成新资料记录，产品不复制。当前/历史状态保存在产品资料记录上，官网明确停用时记录为历史；只知道文件从哪里下载还不足以证明它属于哪款产品。

人工确认值及必要更正说明随业务数据保留；未确认候选和采集差异保存在运行库，确认后再确定资料所属产品。文件和快照保存在 MinIO，内容哈希只用于去重。文件已保存而业务写入失败时，重试复用已有文件，不另建一套业务状态机。

### 调度、重试与断点

业务任务按协会索引同步、公司资料获取组织，运行库保存任务与分页/产品处理单元的进度，Redis 队列负责执行调度。先保存进度再确认单元完成。恢复允许重复读取，但不重复创建产品、同一文件和同一关联。

页面临时失败由请求层有限重试；耗尽后记该项失败并继续其他项。任务层重试只处理进程或基础设施异常，恢复未完成项，不因单页失败重复整批任务。取消停止新工作并尽可能中止活动请求，已保存结果保留；重试与续跑跳过已完成项。

全局并发与公司域名访问频率共同生效；多个 Worker 的并发不能放大同一官网的总限额。同公司重复任务合并或排队。定时触发集中于调度层，Adapter 不自行定时。首次启动不自动触发全库采集，在中台启用任务或计划。

并发、访问间隔、超时与重试次数在入口小规模验证后配置，不作为产品业务规则，也不提前宣称生产性能。

### 成熟组件候选及职责

以下是基于官方文档的设计建议，具体版本在工程建立时锁定：

- **BullMQ**：Redis 上的业务任务、Worker 和定时触发。使用任务级重试处理执行异常，不承担每个网页的发现逻辑。[Worker 并发](https://docs.bullmq.io/guide/workers/concurrency)、[任务重试](https://docs.bullmq.io/guide/retrying-failing-jobs)、[Job Schedulers](https://docs.bullmq.io/guide/job-schedulers/)。
- **Crawlee**：一次业务任务内的 HTTP/浏览器请求、动态页面队列、页面并发与有限请求重试。需要 JavaScript 才用浏览器路径；同一页面不同时作为业务任务和页面请求双重调度。[HttpCrawler](https://crawlee.dev/js/api/http-crawler/class/HttpCrawler)、[PlaywrightCrawler](https://crawlee.dev/js/api/playwright-crawler/class/PlaywrightCrawler)、[请求队列](https://crawlee.dev/js/api/core/class/RequestQueue)。
- PDF 下载单独明确支持的响应类型；不能假设 HttpCrawler 默认会处理 PDF。轻量格式检查不进行表格或正文抽取。

框架请求队列不代替运行库业务断点；单个 Crawler 的并发上限不等于所有 Worker 的公司总限流。[Crawlee 并发与重试选项](https://crawlee.dev/js/api/basic-crawler/interface/BasicCrawlerOptions)、[BullMQ 幂等任务](https://docs.bullmq.io/patterns/idempotent-jobs)。

### 状态与中台

| 对象 | 展示口径 |
| --- | --- |
| 销售状态 | 在售、停售/停用组、未知；协会原始状态及销售时间逐条保留 |
| 任务 | 排队、运行、完成、部分失败、失败、已取消；处理单元另存断点 |
| 产品某类资料 | 尚未执行、未找到、已下载、下载失败、归属待确认；中断附原因 |
| 已关联文件 | 当前或历史；版本关系不明时不自动替换当前资料 |

“未找到”仅指本轮已搜索范围内未找到；“不适用”须有明确来源或人工确认，不能从缺失倒推。资料情况由已关联资料与最近运行结果合并展示，不在产品表塞入重试和网络错误。

中台包含产品列表与详情、公司管理、采集任务、待确认事项和运行设置。产品页支持公司/名称/在售状态筛选、四类资料、原件预览、来源与历史资料。任务页支持范围选择、进度、取消、失败重试及续跑。

API 建议按 `/companies`、`/products`、`/documents`、`/crawl-tasks`、`/review-items` 分组；任务创建立即返回 ID，SSE 推送进度，断线可重新查询任务状态。所有查询、下载和维护入口直接通过业务 API 提供，不要求先接 Agent。

首轮配置内部访问认证及独立服务配置，为未来上线保留部署入口，不建设多租户平台。

## 实施与验收设计（待整体审阅）

1. **工程与环境**：React 中台使用 pnpm，Python 后端使用独立虚拟环境；以 Docker Compose 提供 MySQL、Redis 与 MinIO，产品库及运行库分别配置。
2. **P1**：Association Adapter、分类分页任务、公司/产品入库、在售更新、中台查询。用真实类别验证翻页、重复执行、状态更新与人工更正保护，报告类别/页范围、源站报告数、实际读取数、去重数。完整类别遍历报告用于当次覆盖验收，单页样例不能代表全库。
3. **P2 Core 与首个 Adapter**：从 P1 选择真实产品，验证官网发现、下载、轻量格式检查、快照、归属和预览；测试正常 PDF、错误网页、失效地址、共用资料和歧义。真实样例与构造测试分别记录。
4. **逐家公司接入**：按统一接口扩展官网，分别统计接入公司、涉及产品及四类资料结果；新增公司不复制 Core、不按产品定制规则。
5. **运行验证**：多任务并发、公司频率控制、失败重试、取消、进程重启后续跑和重复任务结果不重复。以实际结果说明能力，不虚构并发性能。

任务完成率、产品覆盖及资料获取情况分别统计并明确分母；格式正确不代表内容正确。Python 契约与业务测试使用 unittest，前端使用 Vitest。联网实测单独记录。
